# 实验卡：E4 —— C2 + 笔记过程奖励（低成本 80 步方案；E5 已取消）

> 状态：**设定已冻结（2026-11-10，用户确认 λ=0.2、单卡、约 ¥85、14 小时硬上限）**，见下方「冻结设定」。2026-11-08 用户选定方案 A；同日用户决定**取消 E5**。数字只能来自 runs/<run_id>/。
> 取代 PLAN §7 原定的 E4 / E5（C2、C0 第 2 个 seed）。代价：没有 seed 重复，报告中须说明。

## 动机（来自 D9 / RQ2，见 `d9_sealed_eval.md`、`d10_rq2_note_quality.md`）
- C2（模型自写笔记）训练后很少写笔记：训练轨迹中有 note 的比例 10.6%（第 1–10 步）→ 3.8%（51–60）→ 4.4%（141–150）；dev 每 500 题的笔记数 58（step 0）→ 21 / 24（step 40 / 60）→ 14（step 150）。C2 因此接近「只看最近一轮文档」，与 C1 一样在跨轮题上掉分（2Wiki C2 0.498 vs C0 0.656，McNemar p≈1e-14；C0 步数 ≥2 的子集 C2 0.348 vs C0 0.631）。
- RQ2：模型**一开始写的笔记质量就不差**——格式全部有效、明确幻觉约 2%、引用段落属于官方 supporting fact 文档的比例 0.86（训练第 1–10 步）。RL 后数量降到约三分之一，质量没有变好（更贴原文，但命中支撑文档 0.86 → 0.75）。
- D9 中写了笔记的轨迹 EM 更低（test 0.29 vs 0.54）、步数更多：只用 EM 奖励时，GRPO 组内比较把「写笔记」和「答错」联系起来，可能是笔记被压下去的原因（相关性证据）。

## E5 取消的理由（2026-11-08 用户决定）
- E5（SFT 冷启动）要检验的是「初始策略不会写笔记」。RQ2 已显示初始笔记格式全对、质量不差，这个假设基本被排除。
- 需要说明的保留：RQ2 排除的是「不会写」，没有排除「写得太少、探索不足」——训练开始时只有约 11% 的轨迹写笔记，SFT 仍可能通过提高初始笔记率帮助 RL。取消 E5 主要出于预算考虑；报告中如实写明这一点，不写成「E5 已被证伪」。

## E4：C2 + 笔记奖励（相对 E2 只改奖励）
- 奖励：`r = EM + λ · bonus`，bonus 只在以下条件同时满足时给：最终答对、检索 ≥ 2 轮、至少有一条笔记写在最后作答步之前。bonus = 笔记引用的文档（`Note.source`）中属于 HotpotQA 支撑事实文档（supporting_facts 标题）的比例，每条轨迹最多 1；λ 候选 0.2（冻结前定）。
- 防钻空子：只在答对时给、设上限；笔记条数和长度已有上限（每步 3 条、每条 ≤300 字符）；开跑后监控笔记率与「答案原文写进笔记」的比例。
- 需要的实现：用 HF `hotpotqa/hotpot_qa` distractor train（已下载到 `data/raw/hotpot_qa_hf/`，与训练题按问题文本匹配）接上 supporting_facts；在奖励函数里读轨迹的笔记与引用文档标题；单测覆盖 bonus 计算和各条件。约半天到一天。
- 其余与 E2 完全相同（LoRA、lr、64×8、选择规则）。

### 低成本方案（2026-11-08 用户要求评估并记录）
- **训练 80 步，而不是 150 步。** 依据：E2 的笔记率坍缩在前 60 步基本完成（10.6% → 3.8%），E2 dev EM 在 step 80 已到 0.510（step 150 为 0.512），E0 的最佳 checkpoint 也在 step 80。80 步足以看清两件事：笔记率是否不再坍缩，以及多轮题 EM 是否回升。
- **评分判断：80 步足以验证「过程奖励能否阻止笔记坍缩、改善多轮题」这个假说**，但前提是比较对象也取 80 步——**对照用 E2 的 `adapters/step_80`**（已存在，dev 0.510），在同样的 5 步评测上重新评一次，保证 E4 与 E2 只差奖励、训练步数相同。不能拿 80 步的 E4 去和 150 步的 E2 比。
- 局限：80 步看不到「后期是否再次坍缩」或奖励被钻空子的晚期行为；若 80 步结果明确为正，再考虑续训到 150 步（checkpoint 可续训，不浪费前 80 步）。
- **评测只跑 5 步**（HotpotQA test、MuSiQue、2Wiki），不跑 10 步外推（D9 已显示 5 → 10 步不改变组间差距）。
- 选择规则：E4 在 dev step 20 / 40 / 60 / 80 中取 dev EM 最高者（与主实验同一规则，限于 80 步内）。
- 预计（估计，以账单为准）：E4 训练约 80 × 420 秒 ≈ 9.5 小时 + 4 次 dev 评测和存档 ≈ 10 小时，约 ¥70；评测 E4 选中 adapter + E2 step_80 各三套 5 步（2Wiki 约 28 分钟 / 组，其余约 8 分钟 / 组）约 1.5 卡时，约 ¥10；合计约 ¥80。单卡机即可。

## 评测侧的工程优化（来自 D9 的问题，若跑 E4 评测可直接采用）
D9 中 2Wiki 单组评测约 28 分钟，其中前约 10 分钟 GPU 利用率为 0；10 步评测两次因容器内存（110GB）触顶被杀，worker 被迫从 8 降到 2。原因：每次 `val_only` 冷启动时，每个 `AgentFlowWorker` 进程各自用 `json.loads` 逐行解析 590 万行语料（3GB 文本在进程内变成大量 Python 对象），并用 `faiss.read_index` 把 23GB Flat 索引读进进程私有内存；再叠加反复读文件累积的约 40GB 页缓存。
- **A：只读内存映射 + 语料按需读取。** 索引改为 `faiss.read_index(path, faiss.IO_FLAG_MMAP | faiss.IO_FLAG_READ_ONLY)`，多个 worker 共享同一份页缓存，不再各复制 23GB；语料改为「字节偏移索引 + 按需读取」或 Arrow / Parquet 内存映射，只在命中 top-5 时取文本。需要先在所用 faiss 版本上确认 `IndexFlat` 支持 mmap 读取（若不支持，可把向量存成 `.npy` 用 `numpy.memmap` 打开再做内积检索）。改的是 `third_party` 的检索工具，按规则用 patch 记录。
- **B：常驻检索服务。** 把 2Wiki 检索器作为单实例常驻进程（本地 HTTP 服务或 Ray detached actor）启动一次，多次 `val_only` 评测复用，消除每次约 10 分钟的冷启动，并恢复 8 个轻量 agent worker。B 收益更大（同时去掉重复冷启动），但改动也更大；A 改动小、先解决内存问题。
- 两者都不改变检索结果（同一索引、同一编码模型、精确检索），不影响与 D9 的可比性；采用前用 D9 的检索冒烟 5 题核对 top-5 完全一致。

## 冻结设定（2026-11-10，开跑前提交；之后不再改）
- run_id：冒烟 `e4smoke_c2nb_q3-0p6b_lora_pro6000_<日期>`；训练 `e4_c2nb_q3-4b-2507_lora_pro6000_<日期>`；评测 `d9e4_<数据集>_<e4s{选中步}|e2s80>_q3-4b-2507_lora_pro6000_<日期>`。驱动 `scripts/autodl/e4_run.sh all`。
- 唯一变量（相对 E2）：奖励 = EM + 0.2 · bonus（`src/ssrl/note_bonus.py`，单测 `tests/test_note_bonus.py` 10 项）。flow `configs/flows/ssrl_c2_e4.yaml` 与 `ssrl_c2.yaml` 只差 `note_bonus_lambda: 0.2` 和 `supporting_facts_path`。bonus 条件：答对、检索 ≥ 2 轮（含自动首搜）、写过笔记；bonus = 笔记引用的文档以该题 supporting fact 标题开头的比例（∈ [0, 1]）。λ = 0 时代码路径与 E0–E3 完全相同。
- supporting fact 标题表：`scripts/build_supporting_facts.py` 由 HF `hotpotqa/hotpot_qa` distractor train + validation 生成，按问题文本匹配，Agent-R1 train 90,447 题、validation 7,405 题全部匹配；文件 sha256 `67a20d69…`（驱动脚本开跑前校验）。
- 训练：与 E2 完全相同（Qwen3-4B-Instruct-2507、LoRA r32 / α32 / all-linear、lr 1e-5、64 题 × 8、同数据同顺序、max_prompt 8192、单步 response ≤1024、不加 KL），只是总步数 80；每 20 步存档 + dev_select 500 题 greedy 评测（开训前也评一次）。日志里 `acc` 仍是 EM，`reward` 含 bonus，另记 `note_bonus`。
- 选择规则：dev EM（`acc`）最高的 step（20 / 40 / 60 / 80，不含 0），并列取更早。
- 评测：E4 选中的 adapter 与 **E2 `adapters/step_80`**（对照，同为 80 步）都在 HotpotQA test 1000、MuSiQue 500、2Wiki 500 上 5 步评测；走 D9 同一路径，flow 用 `ssrl_c2`（只算 EM，口径与 E2 / D9 一致）；2Wiki 用 2 个 agent worker、加载前清页缓存（D9 的处理）。封存 test 对 E4 只跑这一次。
- 冒烟验收（0.6B、4 步，不通过不开训）：训练正常退出；每个 rollout 都带 `note_bonus`；每条轨迹的 dump `score` = `acc + 0.2 · note_bonus`（`score` 来自 `token_level_scores`，即训练实际使用的奖励）；所有问题都在标题表里。
- 硬件 / 预算：单卡 RTX PRO 6000 96GB（西北B，私有镜像），数据盘 150GB；预计约 12 小时、约 ¥85（冒烟约 ¥4、训练约 ¥70、评测约 ¥10，按单卡约 ¥7/h 估）；`all` 设 14 小时硬上限自动关机。
- 停止规则：冒烟不通过 → 不训练，修复后重跑冒烟；训练崩溃 → 同命令从最近 checkpoint 续训（不改配置）；训练中笔记率与「答案原文写进笔记」比例一起监控，出现明显钻空子（如笔记大量直接抄答案）照常跑完并在结果中报告，不中途改奖励。

## 判读（事先写定）
- 主指标：5 步评测（test / MuSiQue / 2Wiki）上 E4 vs E2（同为 80 步），重点看「C0 步数 ≥2 子集」与 2Wiki；同时列出 C0 / C3 作参照。次指标：训练笔记率曲线、笔记命中支撑文档的比例（RQ2 同方法）。

## 结果（2026-11-10；run：`e4smoke_c2nb_q3-0p6b_lora_pro6000_20261110`、`e4_c2nb_q3-4b-2507_lora_pro6000_20261110`、`d9e4_*_pro6000_20261110`）
- 机器 / 时长 / 费用：单卡 RTX PRO 6000（驱动 580.82.09，容器内存上限 110GB），00:49 开机 → 14:55 关机，约 14.1 小时，按约 ¥7/h 估约 ¥99（以账单为准）。结果存文件存储 `/root/autodl-fs/ssrl-runs/`（含 adapters），本地 `runs/`（不含 adapters），逐文件核对一致。
- 冒烟：256 条轨迹 `score = acc + 0.2·note_bonus` 全部一致、问题全部可查；但 0.6B 没有 bonus > 0 的轨迹。4B 训练前 3 步补查正的奖励路径：符合条件的 29 条中 28 条拿到 bonus（1 条笔记没引用支撑文档），训练奖励逐条与 EM + 0.2·bonus 一致。
- 异常与处理（均未改配置）：
  - 第 24 步左右崩溃（vLLM wake_up 时 worker 被杀；容器 memory.events 中 max 计数约 57.6 万；step 20 刚写完 18GB checkpoint）。按停止规则用同一命令从 step 20 续训（`train.attempt2.log` 确认模型 / 优化器 / RNG 从 `global_step_20` 恢复），丢失第 21–24 步；续训期间后台每 2 分钟清大文件页缓存，第 40 步存档时内存又触顶后改为每 15 秒清 checkpoint 页缓存，之后未再触顶。脚本 `e4_resume.sh`（存于 run 目录）。
  - 因崩溃多用约 1 小时，07:01 把硬上限从 14 小时延长到约 16 小时（最多多约 ¥14，未超过 ¥20 确认线）；实际 14:55 结束。
  - 机器差异：E2 在双卡机与 E3 共享容器训练，E4 在单卡机（110GB）独占；训练配置、数据、种子相同。
- 训练行为（训练 rollouts，有笔记的轨迹比例）：第 1–10 步 10.0% → 11–20 步 13.2% → 21–30 步 19.0% → 31–40 步 29.8% → 41–50 步 33.1%（E2 同期 10.6% → 8.8% → 7.1% → 6.0% → 5.4%）。每条写笔记的轨迹平均笔记数 1.20 → 1.61，笔记含标准答案比例 0.64 → 0.72（开训时已是 0.64），未见明显钻空子。检索轮数与 E2 相同（31–44 步每条轨迹 1.40 轮），但单独写笔记的步使每条轨迹总步数 1.43 → 1.78、用满 5 步预算的轨迹 4.2% → 6.5%，每步训练时间约 413 → 492 秒。
- dev（500 题）：step 0 / 20 / 40 / 60 / 80 EM = 0.440 / 0.476 / 0.490 / 0.494 / 0.496（E2 同步数 0.440 / 0.466 / 0.494 / 0.502 / 0.510）；每题笔记数 0.108 / 0.20 / 0.59 / 0.34 / 0.39（E2 0.116 / 0.096 / 0.042 / 0.048 / 0.036）。按规则选中 **step 80**。
- 主结果（5 步评测；E4 step 80 vs E2 step 80，同题配对 McNemar「E4 对 E2 错 / E4 错 E2 对」）：

  | 数据集 | E4 EM | E2 step 80 EM | 配对检验 | C0 步数 ≥2 子集 E4 / E2 | 每题笔记数 E4 / E2 | 平均步数 E4 / E2 |
  |---|---|---|---|---|---|---|
  | HotpotQA test（1000） | 0.513 | 0.519 | 32 / 38，p=0.55 | 0.361 / 0.373（n=263，p=0.72） | 0.42 / 0.034 | 1.81 / 1.44 |
  | MuSiQue（500） | 0.196 | 0.198 | 16 / 17，p=1.0 | 0.196 / 0.192（n=250，p=1.0） | 0.49 / 0.034 | 2.39 / 2.02 |
  | 2Wiki（500） | 0.472 | 0.452 | 32 / 22，p=0.22 | 0.310 / 0.286（n=290，p=0.36） | 0.26 / 0.056 | 2.65 / 2.40 |
  参照（D9）：2Wiki C0 0.656、C3 0.664、C2（E2 step 150）0.498。
- 结论（按事先写定的判读规则）：**属于「笔记率上去了但 EM 没有显著提升」这一支。** 过程奖励成功阻止了笔记坍缩（训练中笔记轨迹 10% → 33%，评测时每题笔记数是 E2 的 5–14 倍），但三个数据集上 EM 与 E2 同步数都没有显著差别；2Wiki 上 +2.0pp（多轮子集 +2.4pp）方向为正但不显著，且离 C0 / C3（约 0.66）仍差约 19pp。笔记被写下了，却没有转化为跨轮推理的准确率；可能原因：笔记多为单独一步写的，占掉部分步数预算（用满 5 步的轨迹增多）；奖励只要求「引用了支撑文档」，不要求笔记内容在后续被用上。在本设定下，规则压缩（C3）仍是更实际的选择。
- 局限：单 seed、80 步；对照是 E2 的 step 80，不是 E2 最终选中的 step 150；E4 与 E2 运行机器不同（内存余量不同，训练配置相同）。
